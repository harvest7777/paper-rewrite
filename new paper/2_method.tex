\section{Method}
\label{sec:method}

The design goal was that source code be the \emph{only} thing differing between
the binaries we compare. Everything below follows from that.

\subsection{Sandboxes and build}

Nine clones of GraphViz, all at commit \texttt{23b06521}. One stays untouched as
the baseline. The other eight are agent runs: two agents $\times$ two prompts
$\times$ two repetitions, each on its own branch so the commit histories survive
as artifacts.

The repetitions exist because a single run of an agent cannot distinguish what
the agent tends to do from what it happened to do once. Every run started from
the same commit with no knowledge of the others.

All nine were built with identical CMake flags
(\texttt{-DCMAKE\_BUILD\_TYPE=Release}, Poppler and GVEdit disabled) and
installed to separate prefixes. We checked that each \texttt{dot} loads its own
build of the layout libraries rather than a shared one.

\subsection{The prompts}

Every run received one of two prompts. The base prompt stated the goal --- make
\texttt{dot} faster on large graphs without changing its output --- and
deliberately named no function, file, or phase. Finding the hot code was part of
the task under study. It also:

\begin{itemize}
\item described the target workload shape (large layered graphs with heavy edge
      crossings) without supplying the evaluation graphs, so agents generated
      their own test inputs;
\item required byte-identical \texttt{-Tdot} output and pointed at the 260
      graphs in the repository's own \texttt{tests/} directory;
\item enumerated disallowed shortcuts: detecting or special-casing specific
      inputs, caching layout results across runs, reducing iteration counts or
      loosening convergence thresholds, hardcoding computed values, and
      modifying the test suite;
\item stated that measurement would be independent, that identical builds vary
      by several percent on the target machine, and that a modest honest result
      or no result at all was an acceptable outcome.
\end{itemize}

The iteration-count prohibition matters most. Crossing minimization is
iteration-bounded, so cutting its limit yields a large, real, reproducible
speedup that is not an optimization. The prompt asked for that to be reported as
a finding rather than shipped as a change.

The second prompt is the base prompt with one section added. It observes that
\texttt{dot} is single-threaded while the machine's other cores sit idle, asks
the agent to treat concurrency as the primary strategy rather than an
afterthought, suggests where independent work might be found (loops over ranks,
components, or candidate orderings), and states that output must not depend on
thread count or scheduling. It also asks for thread counts and per-thread-count
speedups in the report, and for an explanation wherever the agent concluded
something could not usefully be parallelized. Everything else --- workload,
constraints, disallowed shortcuts, deliverable --- is word for word the base
prompt.

We added it because no run under the base prompt introduced concurrency of any
kind, in either agent. Whether that is what agents prefer or merely what they
did here is exactly the sort of question a second prompt can separate.

Agents worked autonomously with no turn or time limit, committing incrementally
and writing a report of what they profiled, changed, abandoned and verified.
Neither had access to the evaluation harness, the benchmark graphs, or the other
agent's sandbox.

\subsection{Evaluation graphs}
\label{sec:graphs}

Graph generation is deterministic. Nodes are split into equal layers and each
points at \texttt{fanout} random nodes in the next layer, which is what creates
the crossings layout has to resolve.

These parameters keep every phase measurable. Wider ranks make crossing
minimization so expensive that nothing else is visible next to it.

The generator does not pin ranks. Wrapping each layer in \texttt{rank=same} is
legal DOT, but it supplies the answer the ranking phase exists to compute: on
otherwise identical graphs that reduces ranking from $267$\,ms to $1$\,ms and
removes the phase from measurement.

\subsection{Measurement}

All timings use \texttt{hyperfine} 1.20.0~\cite{peter2023hyperfine} with 10
warmup and 10 timed runs. All binaries for a graph are measured in one
invocation, seconds apart under the same thermal conditions; separate
invocations produce order-dependent bias large enough to swamp the effects we
are looking for.

\texttt{hyperfine} runs all repetitions of one command before starting the next,
so a fixed order always hands the same binary the tail of any drift. We rotate
the starting position and pool: four orderings, 40 timed runs per binary per
graph. With nine binaries a full rotation would take nine orderings; four is
enough that no binary sits at the tail of drift in more than one of them, and it
keeps a single invocation under an hour.

The rotation also supplies the noise floor. The baseline is measured four times,
once per ordering, so the spread among its own means is what the protocol
reports for a program compared against itself.

Binaries that use threads pick their own thread count, and we measure whatever
they pick rather than imposing one: that is what a user running the binary
would get. The two differ --- one defaults to every online core, the other to
the performance cores only --- so Section~\ref{sec:threads} measures each of
them again at one thread, which is what separates a threaded gain from a serial
one.

Two conventions hold throughout this paper. A \emph{mean} is always the
arithmetic mean of individual timed runs, with warmup runs excluded. A
\emph{speedup} is always the ratio of two such means --- never the mean of
per-run or per-ordering ratios. The two are not equal, and every ratio we report
is the former.

We prefer this to benchmarking separately-built identical binaries, which we
also tried. Those would be measured in their own invocation, with a different
command set and a different thermal profile from the runs they are meant to
bound. The baseline's spread is measured in the same invocations, on the same
graphs, against the same competitors as the results it guards.

\subsection{Phase instrumentation}

Phase costs are measured inside the process. An identical patch --- applied by
cherry-pick, so all nine diffs match byte for byte --- reads a monotonic clock
around each phase and writes the elapsed time to standard error. It is off
unless an environment variable is set, so layout output is unchanged and the
correctness check below is unaffected.

Parsing and output writing happen outside the layout routine, so the phases do
not sum to wall clock. We report the difference rather than assigning it to a
phase.

\subsection{Correctness checking}

Correctness is checked on \texttt{dot -Tdot} output, not a rendered image. The
text format is deterministic, so byte-identity means something; image comparison
would fold in rendering and floating-point behaviour we are not studying. We
also read both diffs against the prompt's list of disallowed shortcuts.

\subsection{Platform}

Experiments ran on an Apple M4 Pro (12 cores: 8 performance, 4 efficiency),
24\,GB unified memory, macOS 26.5.2, with Apple Clang 17.
