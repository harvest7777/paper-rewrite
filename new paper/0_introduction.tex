\section{Introduction}
\label{sec:intro}

Coding agents are now routinely asked to modify real software. Most evaluations
of that ability measure whether an agent can make a failing test pass
\cite{jimenez2024swebench} --- a task with a clear oracle, where success is
checkable by running the suite. Performance optimization has no such oracle. An
agent asked to make a program faster must first decide \emph{what} to make
faster, and a plausible-looking change that helps nothing is indistinguishable
from a real improvement unless someone measures carefully.

This paper asks a narrow version of that question. Given a mature C codebase, no
hint about where time is spent, and an instruction only to make the program
faster without changing its output, can a coding agent find a genuine bottleneck
and fix it?

We use the \texttt{dot} layout engine from GraphViz~\cite{ellson2001graphviz}.
It is real, widely deployed software rather than a benchmark written for the
occasion; its layered pipeline
\cite{sugiyama1981methods,gansner1993technique} has distinct phases whose costs
can be measured separately, so a speedup can be attributed rather than merely
observed; and its text output is deterministic, which makes ``the output did not
change'' checkable rather than a judgment call.

\paragraph{What we did.}
Two agents --- Claude Code and Codex --- each ran four times, for eight runs in
total. Each run received its own pristine checkout of GraphViz pinned to commit
\texttt{23b06521} and a prompt naming no target function, file, or phase. Two
runs per agent used a base prompt; the other two added a section asking the
agent to treat concurrency as its primary strategy, because no run under the
base prompt had introduced any. Every prompt forbade the shortcuts that would
fake a win: caching layout results, special-casing inputs, and reducing the
iteration counts that govern layout quality. No run had access to the evaluation
harness, the graphs it uses, or any other run's sandbox. We rebuilt all eight
results ourselves and measured them against an untouched baseline, on three
graph shapes at two node counts.

\paragraph{What we found.}
No run failed to locate expensive code. All eight reports name the same two
regions --- crossing minimization, and the network simplex serving ranking and
coordinate assignment --- and every binary that shipped produced byte-identical
layout output.

They separate on breadth. All four Claude runs went into network simplex as well
and improved three phases, measuring $1.39\times$ to $4.02\times$ end-to-end.
Of the four Codex runs, one improved crossing minimization only
($1.02\times$ to $1.33\times$), and \emph{three shipped no layout code at all}:
each built a change, measured it against the workload the prompt described,
found it slower or unprofitable, and reverted it. Those three binaries are the
baseline recompiled, which we report as a deliberate outcome rather than a
failure --- and which gave us an unplanned null sample showing our per-phase
noise floor is optimistic.

Repetition mattered more than we expected. Claude's two base-prompt runs differ
by $1.39\times$ against $1.67\times$ on one shape; Codex's differ in whether
anything shipped at all. A single run of an agent does not characterize it.

The parallelism prompt produced the subtlest result. Its two Claude runs land
close together end-to-end, but re-measuring each at one thread shows they are
not the same kind of result. One put its concurrency in crossing minimization
and is rewarded on wide graphs at any size --- threads account for $2.78\times$
of its result on the densest shape --- and not at all on narrow ones. The other
put its concurrency in network simplex behind large size thresholds: its threads
are worth $1$ to $16\%$ at 5{,}000 nodes and $21$ to $36\%$ at 10{,}000, when
the input finally reaches the size it was written for. Each design pays exactly
where the input makes its phase expensive.

Which phase dominates is a property of the input, and two things move it. At
identical node count, shape moves it hardest: crossing minimization ranges from
$12.4\%$ to $64.8\%$ of layout time. Size moves it too, and always the same way
--- doubling to 10{,}000 nodes cuts that phase's share on every shape and hands
the difference to network simplex. Each combination sets a different ceiling, and
on the sparsest shape every Claude run exceeds the ceiling available to any
crossing-minimization optimization at all. The ceilings themselves fall with
size, so the strategy of optimizing that one phase is worth least on the largest
graphs.

\paragraph{Contributions.}
\begin{itemize}
\item A controlled protocol for evaluating agent-driven optimization: balanced
      command ordering, which also yields an empirical noise floor from the
      baseline's own spread across orderings, and a held-out evaluation
      harness.
\item Phase-resolved measurements of eight agent runs across three graph shapes
      at two node counts, with per-phase attribution and the input-dependent
      ceiling that bounds it, plus repetitions that show how far two runs of one
      prompt can diverge.
\item A thread-resolved decomposition of the runs that shipped concurrency,
      separating what their threads buy from what their serial changes buy ---
      the measurement that decides whether a parallel-looking result is one.
\item Evidence that a floor built from the baseline against itself understates
      cross-binary variation, from three shipped binaries that turned out to
      contain no change.
\item A complete artifact: pinned source, every run's diff, commit history and
      report, raw timing data, and the figure-generation scripts.
\end{itemize}
